problem Where the terminal stops helping

Running one coding agent is a pleasure. Running five is a different job, and the terminal stops being the right place to do it from.

You cannot see which is working, which is idle, and which has waited an hour on an answer only you can give. They collide in one checkout. And nothing stands between what one of them wrote and your main branch except you remembering to look.

Every part of kendle below answers one of those three: the sidebar counts what is active, idle and asking, each piece of work gets its own worktree, and kendle gate runs before any push.

today What it does today

All of it is built, and all of it is checkable in an afternoon.

MIT and public. Python's standard library and a tmux config, so there is no dependency to audit. Autopilot built rather than planned. Status: young - a month inside one team's monorepo, just lifted out. It is a working tool, not a mockup, so the useful thing is to go and look.

A worktree and a team per piece of work

Each piece of work gets one git worktree, run by a manager you talk to and six sub-agents: planner, auditor, builder, tester, reviewer, shipper.

You touch the flow three times: you approve the spec, you say plan, you say push. In between, builder, tester and reviewer go round until both pass, and the shipper makes one commit and runs kendle gate. The ready report carries evidence for every line.

Ask, review, logs, housekeeping

  • Ask Read-only questions on the latest base branch, for things that aren't work yet. A good answer can be promoted into a feature.
  • Review Up to three of someone else's changes side by side, read-only, against Gerrit, GitHub or GitLab.
  • Logs The selected feature's services, live, with crash detection.
  • Housekeeping Context and memory per session, idle services stopped, a disk budget that trims build caches but never code or uncommitted work - and everything resumable after a reboot.

Everything the console does is also a command, so a script or another agent can drive it.

Autopilot

File an issue, add a label, come back to a merged pull request. The loop only picks up issues carrying your label and opened by an account you listed, so strangers cannot set your teams to work.

A feature team builds each one, its manager standing in for you. kendle then rebases, runs kendle gate, pushes, and opens a pull request for a read-only review session to review. The team itself can never push or use gh; when something needs a person the issue is labelled needs-human and you get a notification.

What it promises

Each of these came from something that went wrong once.

  • Keys never wait on data. The sidebar gathers in a background thread and draws from a snapshot: around 10 ms a keystroke with a hundred sessions open.
  • Quiet is not dead. A role blocked in one long tool call still counts as working; one its manager stopped does not.
  • Idle means nobody worked on it. Measured from the last real message, never from file times: idle sessions keep touching their own transcripts.
  • Nothing is deleted on its own except build caches whose worktree is gone. Sizes are shown first; code and uncommitted work never go.
  • kendle only stops what it started. A port held by anything else is reported, never killed.
  • Commands run plainly. No cd … &&, no VAR=… prefixes: Claude Code's permission rules match the whole command string.

Tests

Every test drives kendle the way a user does: a throwaway git repo, its own tmux socket and state folder, and a stand-in for claude, so nothing touches your real sessions. The suite runs on macOS and Linux on every push, and the README badge carries the count.

install Install

Two commands, and nothing to audit.

macOS or Linux (both tested on every push), Python 3.9+, tmux 3.x, git, and Claude Code (claude on your PATH). Nothing else.

git clone https://github.com/vuhah/kendle.git ~/kendle
export PATH="$HOME/kendle/bin:$PATH"          # in ~/.zshrc or ~/.bashrc

why now Why now

Supervision, not generation, is the half nobody has solved.

Coding agents have recently crossed a line: they run long enough, and independently enough, that one person keeps several of them going at once instead of watching one.

You can check that on the tool kendle is built on, which is also why kendle exists - one terminal stopped being enough for its author. And it moves the bottleneck. When a person wrote the change, writing it was the hard part; when several agents write it, the hard part is seeing across all of them at once and trusting one enough to let its work land. Generation keeps getting better on its own, and a better model does not solve the other half. That one is solved by somewhere to look and something that stops a bad change.

where it's going Where it's going

None of what follows is built. No dates, no promises, no roadmap - this is the picture kendle is aimed at, written down so you can judge whether it is worth aiming at.

Rungs, not five separate wishes, in order: a terminal tool, which is built, then the hub, a new engineer on the team, an assistant over it, away from the desk, and perhaps something people pay for. Each needs the one below it standing first, which is why none is a commitment.

rung one The hub

Today the console is a tmux server on your machine: one socket, one state folder, one sidebar only you can see. That is right while the work is yours, and wrong the moment a second person needs to know what is running - the answer lives on a laptop that may be shut. The picture is that sidebar kept somewhere a team opens. What changes is not the view but where the truth lives, and that is the whole difficulty. Every rung above needs it first.

rung two A new engineer on the team

It is Monday morning. You open the hub before you have finished your coffee, and the top of the list is a feature nobody started on Friday: checkout double-charges on retry, filed as an issue, picked up overnight, now sitting on one question. It is the question a new hire asks in their first week - the two retry paths in the API disagree about what counts as the same attempt; which one is the rule? - and you answer it in a sentence. By the time you look again there is a spec, a plan an auditor has argued with, and one commit that passed the gate. What makes that different from a code generator is the question: it had read the repository and the conventions, found the contradiction, and knew that settling it was not its call.

rung three An assistant over the hub

The console today is keys: a to ask, p to promote an answer into a feature, g to review someone else's change, K to stop a session. Quick once they are in your fingers, a wall before that. The picture is saying it instead: start the two features from yesterday's issues, tell me what is blocked, tell me why the gate failed. Nearer than it sounds, because everything the console does is already a plain command. The keys stay either way.

rung four Away from the desk

Autopilot already runs without you: an issue goes in, a team builds it, the loop stops when something genuinely needs a person. The gap is that the person has to be at the terminal, and an overnight run that stalls at midnight has wasted the night. The picture is a phone: the run says in one line what it is stuck on, you read the diff, you answer the one question, and it carries on. Not a dashboard to watch - one notification and one answer. It is also why this page has to work at 320 pixels wide.

rung five Something people pay for

Some of this may become a paid product one day, and that sentence is as far as it goes. No price, no tier, no date, no business model - kendle does not have one yet, and inventing one would be the same lie as inventing a user count. What can honestly be said is the shape: a hub that holds a team's work is something somebody has to run and pay for, and agents that work while nobody watches spend money the whole time. kendle is MIT today, and the console is not the part anyone would charge for. If that changes it will be written here after it is true, not before.

What would have to be true first. The same three walls stand in front of all five. Shared state: every future above needs a version of that one tmux server and state folder which two people can open at once. Trust: once a team shares one place, who may start a session and what an agent may run become somebody's responsibility rather than settings on your laptop. Cost: unattended sessions spend tokens for as long as they run, and a hub is only worth having if the bill is predictable before the month ends. Those three are also the honest answer to the paid question.

still open What we do not know yet

No answers here - and these are questions, not an order of work.

  • Where does the shared state live, and does somebody else have to run it?
  • Where is the trust boundary - who may start a session, whose issues a loop acts on, what an agent may run?
  • How does the cost of unattended agents stay predictable before the bill arrives?
  • Is this an open-source tool with something hosted beside it, or something else?
  • Which rung is worth building first, and what would tell us we picked wrong?
