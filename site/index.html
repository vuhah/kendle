problem One agent is easy. Several are not.

Running one coding agent is a pleasure. Running five is a different job, and the terminal stops helping: you cannot see at a glance which of them is working, which is idle and which has been waiting an hour for an answer only you can give. They collide in one checkout, so two of them editing the same file becomes yours to untangle. And nothing stands between what one of them wrote and your main branch except you remembering to look before it lands.

Every part of kendle below is an answer to one of those three, which is the only evidence offered here that they are the real problem: the sidebar counts what is active, idle, asking and waiting; each piece of work gets a git worktree of its own; and kendle gate runs before anything is pushed.

today What it does today

Everything in this section is built and running, and all of it is checkable in an afternoon: MIT and public, Python's standard library and a tmux config so there is no dependency to audit, a suite that drives kendle the way a user does and runs on macOS and Linux on every push, and autopilot already built rather than planned. Status: young - it ran for a month inside one team's monorepo and has just been lifted out of it. It is a working tool and not a mockup, so the useful thing to do with this section is go and look.

A worktree and a team per piece of work

Each piece of work gets one git worktree, run by a manager you talk to and a small team of sub-agents: planner, auditor, builder, tester, reviewer, shipper.

You touch the flow three times. You approve the spec, you say plan, and you say push. In between, the planner asks its questions and writes the spec; builder, tester and reviewer go round until they pass; the shipper makes one commit and runs kendle gate. You get a ready report with evidence for every line, and nothing is pushed until you say push.

Ask, review, logs, housekeeping

  • Ask - read-only questions on the latest base branch, for things that aren't work yet; a good answer can be promoted to a feature with the whole conversation as its requirement.
  • Review - up to three of someone else's changes checked out side by side, read-only, against Gerrit, GitHub or GitLab.
  • Logs - the selected feature's services, live, with crash detection.
  • Housekeeping - context and memory per session, idle services stopped, a disk budget that trims build caches but never code or uncommitted work, and everything resumable after a reboot.

Everything the console does is a command too, so a script or another agent can drive it.

Autopilot

File an issue, add a label, and come back to a merged pull request. The loop picks up open issues carrying your label and opened by an account you listed - nobody else's, so strangers cannot set your teams to work.

A feature team builds each one, with its manager standing in for you at the spec, the plan and the push. Then kendle rebases the commit if the base moved, runs kendle gate, pushes, and opens a pull request that closes the issue; a read-only review session reviews it, and the findings go back to the team for as many rounds as you allow. The team itself can never push or use gh - kendle does everything outside the worktree. When something needs a person, the issue is labelled needs-human, the console shows it, and you get a notification.

What it promises

Each of these came from something that went wrong once:

  • Keys never wait on data. The sidebar gathers in a background thread and draws from a snapshot; keystrokes stay around 10 ms with over a hundred sessions.
  • Quiet is not dead. A role blocked in one long tool call still counts as working; one its manager stopped does not.
  • Idle means nobody worked on it - measured from the last real message, never from file times, because idle sessions keep touching their own transcripts.
  • Nothing is deleted on its own except build caches whose worktree is gone. Sizes are shown first; code, branches and uncommitted work are never touched.
  • kendle only stops what it started. A port held by anything else is reported, never killed.
  • Commands run plainly - no cd … &&, no VAR=… prefixes - because Claude Code's permission rules match the whole command string.

Tests

Every test runs kendle the way a user does, against a throwaway git repo with a scratch origin, on a tmux socket, state folder and transcript folder of its own, with a stand-in for claude that records what it was asked to do - nothing touches your real sessions. The whole suite runs on macOS and Linux on every push, and the badge at the top of the README carries the count, where it is generated rather than written down.

install Install

You need macOS or Linux (both tested on every push), Python 3.9+, tmux 3.x, git, and Claude Code (claude on your PATH). Nothing else - kendle is Python's standard library and a tmux config.

git clone https://github.com/vuhah/kendle.git ~/kendle
export PATH="$HOME/kendle/bin:$PATH"          # in ~/.zshrc or ~/.bashrc

why now Why this is worth building now

Coding agents have recently crossed a line: they now run long enough, and independently enough, that one person can keep several of them going at once instead of watching one. You can check that for yourself on the tool kendle is built on, which is also why kendle exists - it was written because one terminal stopped being enough for its author.

That moves the bottleneck: when a person wrote the change, writing it was the hard part, and when several agents write it the hard parts are seeing what is happening across all of them at once and trusting one of them enough to let its work reach your main branch. Generation is the half that got solved in public and keeps getting better on its own. Supervision is the half nobody has solved, and a better model does not solve it - it is solved by somewhere to look and something that stops a bad change, which is what this is.

where it's going Where it's going

None of what follows is built. There are no dates here, no promises and no roadmap - this is the picture kendle is aimed at, written down so you can judge for yourself whether it is worth aiming at.

They are rungs rather than five separate wishes, in this order: a terminal tool, which is built, then the hub, then a new engineer on the team, then an assistant over it, then away from the desk, and then perhaps something people pay for. Each one needs the one below it standing first, which is also why none of them is a commitment.

rung one The hub

Today the console is a tmux server on your own machine: one socket per workspace, one state folder, one sidebar that only you can see. That is exactly right while the work is yours, and it stops being right the moment a second person needs to know what is running - because the answer lives on a laptop that may be shut. The picture is the same sidebar, kept somewhere a team opens: every feature, every session, every gate, in the states kendle already computes. What would change is not the view but where the truth lives, and that is the whole difficulty - the drawing is the easy half. Everything below needs this first, because none of it works while the only copy of what is happening sits on one desk.

rung two A new engineer on the team

It is Monday morning. You open the hub before you have finished your coffee, and the top of the list is a feature nobody started on Friday: checkout double-charges on retry, filed as an issue, picked up overnight, now sitting on one question. The question is the one a new hire asks in their first week - the two retry paths in the API disagree about what counts as the same attempt; which one is the rule? - and you answer it in a sentence, the way you would answer it standing at someone's desk, then go back to your own work. By the time you look again there is a spec, a plan an auditor has already argued with, and one commit that passed the gate, and the thing you have to do is read it. What makes that different from a code generator is the question itself: it had read the repository and the conventions, it found the contradiction, and it knew that settling it was not its call.

rung three An assistant over the hub

The console today is keys: a to ask, p to promote an answer into a feature, g to review someone else's change, K to stop a session. They are quick once they are in your fingers, and a wall before that - the README has a keymap because it needs one. The picture is saying it instead: start the two features from yesterday's issues, tell me what is blocked, tell me why the gate failed on the web lane. This one is nearer than it sounds, because everything the console does is already a plain command, so an assistant would drive the surface a shell script already drives rather than a new one. The keys stay either way; nobody who has learned them should have to give them up.

rung four Away from the desk

Autopilot already runs without you: an issue goes in, a team builds it, and the loop stops when something genuinely needs a person. The gap is that the person has to be at the terminal - a folder-trust question, or a permission the team was not given, will sit there until you are back at your machine, and an overnight run that stalls at midnight has wasted the night. The picture is a phone: the run says in one line what it is stuck on, you read the diff that worries you, you answer the one question, and it carries on. It is not a dashboard to watch, because watching a build from a phone is nobody's idea of a good evening - it is one notification and one answer. This is also why the page you are reading has to work at 320 pixels wide: a site that argues for unblocking a build from a phone and then needs a desk to read is arguing against itself.

rung five Something people pay for

Some of this may become a paid product one day, and that sentence is as far as it goes. There is no price here, no tier, no date and no business model, because kendle does not have one yet and inventing one would be the same kind of lie as inventing a user count. What can be said honestly is the shape of it: a hub that holds a team's work is something somebody has to run and pay for, and agents that work while nobody is watching spend money the whole time they do it. kendle is MIT today, and the terminal console is not the part anyone would charge for. If that changes it will be written here in the same plain words, after it is true rather than before.

What would have to be true first. None of this is a drawing problem, and the same three walls stand in front of all five. Shared state is the first: the console is a tmux server and a state folder on one machine, and every future above needs a version of that truth two people can open at once without one of them winning a race. Trust is the second - once a team shares one place, who may start a session, whose issues an unattended loop will act on and what an agent is allowed to run stop being settings on your own laptop and become somebody's responsibility; autopilot's list of allowed authors and allowed commands is a first sketch of that and nothing more. Cost is the third: sessions that run unattended spend tokens for as long as they run, and a hub is only worth having if the bill is predictable before the month ends rather than after. Those three are also the honest answer to the paid question, because nobody should charge for something until it holds state safely, says no to the right people, and costs what you expected it to.

still open What we do not know yet

These have no answer here, and naming them is cheaper than pretending otherwise. They are questions, not an order of work.

  • Where does the shared state live, and is it something somebody else has to run?
  • Once a team shares one place, where is the trust boundary - who may start a session, whose issues an unattended loop acts on, and what an agent is allowed to run?
  • How does the cost of agents that work while nobody is watching stay predictable before the bill arrives rather than after it?
  • Is this an open-source tool with something hosted beside it, or something else entirely?
  • Which rung is worth building first, and what would tell us we had picked the wrong one?
